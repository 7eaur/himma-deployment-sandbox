## 1) قاعدة النقل الأساسية

لا يتم نقل سلسلة commits التجريبية حرفيًا ولا عمل cherry-pick عشوائي لها. الـSandbox احتوى عدة محاولات تصميمية وطبقات مؤقتة ثم تم التراجع عنها أو حذفها لاحقًا. المطلوب عند تحديث المستودع الرئيسي هو **نقل الحالة النهائية والقرارات النهائية فقط** بعد مقارنة الملفات الحالية في المستودعين.

المبدأ النهائي الذي يجب الحفاظ عليه:

**مصدر محتوى منظم واحد → Seed/Bootstrap آمن → API عرض منظم → قالب طالب واحد → تنفيذ/تقييم منفصل عن العرض.**

ممنوع إعادة إدخال أي منطق يعتمد على تحليل `prompt_text` الخام أو تعديل DOM بعد الرندر لإصلاح المحتوى.

---

## 2) ما لا يتغير من قرارات المشروع الأساسية

- إجمالي Runtime يبقى **125 عنصرًا**.
- التقوية تبقى **35 عنصرًا**.
- المهارات تبقى **44 مهارة**.
- لا تغيير على scoring أو IDs أو stable keys أو منطق التكيف بسبب تعديلات العرض.
- لا تغيير على سياسة R1 للترقية المبكرة.
- الاختبار القبلي والبعدي يبقيان قياسًا محايدًا دون feedback يكشف صحة الإجابة أثناء القياس.
- M08 يبقى External-Gated ولا يُغلق بسبب هذه التعديلات.
- الملفات الصوتية الثابتة غير الموجودة لا يتم اختلاق بدائل لها.

# 3) تحديث الاختبار القبلي

## 3.1 إصدار المحتوى

اعتمد في الـSandbox إصدار عرض قبلي منظم:

`HIMMA-PRETEST-2026-09-01`

المطلوب في المستودع الرئيسي هو الحفاظ على المحتوى الأكاديمي المعتمد مع فصل بيانات العرض إلى حقول صريحة بدل الاعتماد على النص الخام.

لكل سؤال قبلي يجب أن تكون بيانات العرض مفهومة كالتالي:

- `skill`
- `question_text`
- `instruction_text`
- `encouragement`
- `interaction_type`
- `stimulus`
- `options`
- الإجابة/المعيار الصحيح يبقى في طبقة التقييم الحالية

### مثال حاسم — PRE-Q03

العرض الصحيح:

- التعليمة/السؤال: `انظر إلى الحرف، ثم اختر الشكل الآخر للحرف نفسه.`
- Stimulus داخل البطاقة: **`م` فقط**
- الخيارات كأزرار مستقلة: `مـ / سـ / لـ / بـ`

ممنوع إعادة عرض وصف مثل:

`يظهر الحرف «م». اختر الشكل الآخر للحرف نفسه...`

وممنوع تضمين قائمة الخيارات داخل stimulus ثم تكرارها كأزرار.

# 4) تحديث الأنشطة والتقوية

## 4.1 إصدار العرض النهائي

الإصدار الذي يجب اعتباره الحالي في الـSandbox:

`HIMMA-LEARNING-2026-09-01-R2`

يغطي:

- 30 نشاطًا أساسيًا.
- 35 نشاط تقوية.
- الجولات داخل الأنشطة.
- التلميحات.
- العبارات التشجيعية.
- السؤال والتعليمات والـstimulus المنفصل.

## 4.2 عقد الجولة النهائي

كل جولة يجب أن تخرج للواجهة بعقد منظم شبيه بهذا منطقيًا:

```text
round_number
round_total
skill
question_text
instruction_text
stimulus_text
encouragement
hint
interaction_type
options
assets
retry
attempts_used
max_attempts
```

**الواجهة لا تستخرج stimulus أو الخيارات من `prompt_text`.**

`prompt_text` يمكن أن يبقى تاريخيًا/تنفيذيًا داخل قاعدة البيانات إذا كان مطلوبًا للتوافق، لكنه ليس مصدر العرض للطالب.

---

## 4.3 حل مشكلة النص المركب والخيارات المكررة

المشكلة التي ظهرت في الـSandbox كانت من نصوص خام مثل:

`سُ؛ سَ/سِ/سُ`

ثم كانت الخيارات نفسها تظهر مرة أخرى كأزرار.

العرض الصحيح لنشاط استماع كهذا هو:

- السؤال فقط.
- زر `استمع` الخاص بالسؤال.
- الخيارات المستقلة فقط.
- **لا stimulus نصي** إذا كان المرجع يقول إنه لا يوجد نص مستهدف.

تم اعتماد اختبار Regression يمنع عودة النص المركب إلى واجهة الطالب حتى لو كان موجودًا في endpoint التنفيذ الخام.

# 5) مصدر العرض الوحيد للأنشطة

القرار النهائي بعد إزالة التعارضات:

- صفحة النشاط تستخدم Payload عرض منظم من API مخصص للـlearning experience.
- Endpoint التنفيذ/الحفظ يبقى مسؤولًا عن التقييم والتقدم، وليس صياغة ما يراه الطالب.
- لا يوجد `MutationObserver` يغيّر النصوص بعد الرندر.
- لا توجد طبقة DOM Enhancer تضيف/تحذف نصوصًا فوق الصفحة.
- لا توجد CSS polish إضافية خاصة بالأنشطة فوق القالب النهائي.

الـAPI النهائي يجب أن يطلب ويعيد الإصدار الحالي `HIMMA-LEARNING-2026-09-01-R2`، وليس الإصدار القديم بدون `R2`.

# 6) العبارات التشجيعية والتلميح

المنطق النهائي:

- قبل الخطأ: تظهر **العبارة التشجيعية فقط**.
- بعد الخطأ/في إعادة المحاولة: تختفي العبارة التشجيعية ويظهر **التلميح فقط**.
- لا يظهر الاثنان في وقت واحد.
- لا تولد الواجهة تلميحًا ثانيًا Generic فوق التلميح المخزن.
- المرجع المنظم للمحتوى هو الذي يحدد `encouragement` و`hint` كلما كانا متوفرين.

القاعدة:

```text
message = retry ? hint : encouragement
```

مع الحفاظ على neutrality في Pre/Post.

الـBootstrap لا يكفي أن يقول إن القاعدة صحيحة لأن `total_items = 125` فقط.

- Posttest 30/30.

إذا كانت القاعدة قديمة، يتم تطبيق تحديث محتوى **غير هدّام** يحافظ على attempts/history/evidence.

## 13.3 Idempotency

يجب أن ينجح `seed_all` عند تشغيله مرتين دون duplications أو تغيير IDs التاريخية.

في Sandbox نجح فحص seed idempotency في آخر Quality Gate.

# 14) Bootstrap concurrency fix

ظهر في Railway أن عدة Deployments متتابعة قد تتنافس على PostgreSQL advisory lock، وكان الانتظار الحاجب يصل إلى `statement timeout`.

الإصلاح النهائي في Sandbox جعل قفل الـbootstrap **غير حاجب** بحيث:

- instance واحدة تنفذ bootstrap.
- instance أخرى لا تنتظر حتى timeout.
- التطبيق يصل إلى startup دون crash بسبب قفل طويل.

هذا الإصلاح ينقل فقط إذا كان المستودع الرئيسي يحتوي نفس نمط bootstrap/lock عند وقت النقل.
