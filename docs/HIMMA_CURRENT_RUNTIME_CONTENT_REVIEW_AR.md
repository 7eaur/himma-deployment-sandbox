# مراجعة المحتوى الحالي في منصة هِمّة — مرجع العمل المرحلي

> الحالة: CURRENT REVIEW BASELINE
> الغرض: مراجعة واعتماد المحتوى الحالي المعروض فعليًا في المنصة، مرحلة بمرحلة، قبل أي تعديل جديد للمحتوى.
> قاعدة حاسمة: لا تُستخدم الوثائق القديمة أو ملفات المتطلبات السابقة كمصدر أول للمحتوى إذا تعارضت مع محتوى runtime الحالي.

## 1) مصدر الحقيقة الذي سنراجعه

المصدر الأساسي للمراجعة هو المستودع الحالي للمنصة:

`7eaur/himma-deployment-sandbox` — branch `main`

ويُقرأ المحتوى وفق سلسلة التشغيل الحالية نفسها، لا وفق ملفات قديمة منفصلة:

1. `services/api/seed_all.py`
   - هو نقطة تجميع المحتوى المعتمد حاليًا في runtime.
   - يطبق طبقات المحتوى والتصحيحات بالترتيب الذي تستخدمه المنصة فعليًا.

2. الاختبار القبلي الحالي:
   - `packages/content/src/pretest_experience_2026_09_01.json`
   - `services/api/seed_pretest_experience_2026_09_01.py`
   - الإصدار الحالي: `HIMMA-PRETEST-2026-09-01`
   - حالة العقد داخل الملف: `user_approved_2026_09_01`.

3. أنشطة التعلم والتقوية الحالية:
   - بيانات runtime المهيكلة في PostgreSQL بعد تشغيل `seed_all.py`.
   - `services/api/seed_db_runtime_contract.py`
   - `services/api/seed_learning_posttest_projection_runtime.py`
   - الإصدار الحالي للعرض التعليمي: `HIMMA-LEARNING-2026-09-01-R2`.
   - أي تصحيحات أحدث للمستوى الأول أو القصص السمعية أو الخيارات تدخل من طبقات seed الحالية قبل العرض.

4. الاختبار البعدي الحالي:
   - `services/api/seed_learning_posttest_experience_2026_09_01.py`
   - `services/api/seed_learning_posttest_projection_runtime.py`
   - الإصدار الحالي: `HIMMA-POSTTEST-2026-09-01`.

5. قاعدة البيانات الحالية هي مصدر عرض الطالب وقت التشغيل:
   - السؤال والجولة والخيارات وربط الصور/الصوت تؤخذ من ContentItem / ContentStep / ContentOption / ContentAssetLink بعد تطبيق سلسلة seed الحالية.
   - لا يُسمح للواجهة باختراع محتوى بديل عند المراجعة.

## 2) ما تم استبعاده من مرجع المراجعة

- أي توثيق قديم سبق تعديلات سبتمبر 2026 إذا خالف runtime الحالي.
- أي ملخص سابق في المحادثة لا يطابق ما هو موجود حاليًا في `main` وقاعدة البيانات المهيكلة.
- الوثيقة السابقة `HIMMA_CONTENT_EXPERIENCE_REVIEW_DRAFT_AR.md` تم حذفها لأنها بدأت على محتوى غير محدث بما يكفي.

## 3) طريقة العمل المعتمدة للمراجعة

لن نراجع كل المنصة دفعة واحدة، ولن نطبق تعديلات أثناء مرحلة الفهم.

الترتيب:

1. الاختبار القبلي — 30 سؤالًا.
2. المستوى الأول — 10 أنشطة أساسية، كل الجولات.
3. تقوية المستوى الأول — كل الأنشطة والجولات الحالية فعلًا في runtime.
4. المستوى الثاني — الأنشطة الأساسية.
5. تقوية المستوى الثاني.
6. المستوى الثالث — الأنشطة الأساسية.
7. تقوية المستوى الثالث.
8. الاختبار البعدي — 30 سؤالًا.
9. مراجعة شاملة للتناسق بين جميع المراحل قبل التنفيذ.
10. بعد اعتماد الجميع فقط: تنفيذ تعديلات المحتوى والواجهة والوسائط والاختبارات.

## 4) نموذج مراجعة كل عنصر

لكل سؤال/نشاط/جولة سنثبت:

- المعرف الحالي في runtime.
- المهارة المقاسة.
- النص الحالي المعروض للطالب.
- التعليمة الحالية.
- نوع التفاعل الحالي.
- المحفز: نص / صوت / صورة / لا شيء.
- الخيارات الحالية كما تأتي من قاعدة البيانات.
- الصور/الأصوات المرتبطة فعليًا.
- الإجابة/الترتيب الصحيح للاختبار الداخلي فقط.
- ملاحظات العرض الحالية.
- المشكلة إن وجدت.
- الاقتراح بعد فهم الهدف التعليمي.
- هل يحتاج 2 / 3 / 4 خيارات ولماذا.
- هل يحتاج صورة إضافية أو صوتًا أو تعديل ربط.
- الحالة: `REVIEWING` / `PROPOSED` / `APPROVED` / `REJECTED` / `NEEDS_ASSET`.

## 5) قواعد لن نعتمدها آليًا

- لا نضيف خيارًا رابعًا لمجرد الوصول إلى الرقم 4؛ نقرر بعد فهم المهارة.
- لا نخفي النص تحت الصورة قبل التأكد أن الصورة هي الخيار نفسه وليست جزءًا من شرح مطلوب.
- لا نغيّر صياغة سؤال لأن صياغة أخرى تبدو أجمل إذا كانت تغيّر ما يقيسه السؤال.
- لا نصلح التكرار بصريًا فقط؛ يجب التحقق من DB mapping والخيارات الفعلية.
- لا نغيّر الأصول أو الصور قبل معرفة دورها في السؤال وربطها الحالي.

## 7) ملاحظة تشغيلية مهمة

`seed_all.py` يثبت حاليًا عقد runtime كامل ويشترط وجود 125 عنصرًا في قاعدة البيانات بعد جميع الإضافات والتقويات والتصحيحات، مع 30 قبلي و65 عنصر تعلم و30 بعدي. لذلك عند مراجعة المحتوى لن نفترض أن العدد القديم 105 هو كل ما يراه runtime الحالي؛ سنراجع المجموعة الحالية الفعلية بعد كل overlays والتصحيحات.
